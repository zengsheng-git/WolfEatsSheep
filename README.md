# 三炮十五兵走法提示工具 🎯

民间棋"三炮十五兵"（兵炮棋）的连线分析助手：监听目标游戏窗口，实时识别棋盘局面，内置 AI 引擎分析并提示最佳招法。架构参考开源项目 [atopx/chessboard](https://github.com/atopx/chessboard)（中国象棋学习助手），将其中的象棋规则、YOLO 识别与 Pikafish 引擎替换为三炮十五兵的实现。

## 规则（标准版）

- 5×5 交叉点棋盘；炮 3 枚开局在 a0/c0/e0，兵 15 枚填满第 2~4 排，**炮先行**
- 双方每次沿线横竖走一步到相邻空点
- **炮**隔恰好一个子（炮架，兵炮皆可）"隔山打"吃掉其后第一枚兵（象棋炮吃法）
- 三炮全部无路可走 → **兵胜**；兵被吃到剩 3 枚 → **炮胜**；连续 60 步无吃子判和

## 功能

- 📷 **实时棋盘识别**：经典 CV 管线（颜色分割 + 连通域 + 网格拟合），无需训练模型
- 🤖 **内置 AI 引擎**：Rust 实现的 negamax + alpha-beta + PVS/LMR + 迭代加深 + 置换表 + 静态搜索，替代外部引擎
- ♾️ **可选全量破解（完美着法）**：离线回溯分析求解全部局面（方法论参考 [0irina/lang-chi-yang-qi](https://github.com/0irina/lang-chi-yang-qi)），
  生成值表后任意局面（炮胜/兵胜/和）直接给出严格最优着法，见下文"完美着法表"
- 🎯 **招法提示**：最优着法箭头 + 中文记谱（"炮 b1 吃 b4"）、后续变化主线、次优着法
- ⚙️ **提示强度分级**、搜索深度/时间、次优分差阈值、我方阵营（执炮/执兵）配置

## 引擎配置建议

设置抽屉里的四项，按"永远要最强招"的目标推荐：

| 配置项 | 推荐值 | 作用说明 |
|---|---|---|
| 提示强度 | **最强(不限)** | 降智开关：1~5 档会**无视深度设置**、固定只搜 2~6 层并跳过查表，用于陪练 |
| 深度 | **16（拉满）** | 搜索层数**上限**而非目标，和时间取先到者——拉满不会变慢 |
| 时间(秒) | **1.0**（不介意提示晚 1 秒可 2.0） | 只影响尚未查表的局面；设太大每步提示刷新变慢，得不偿失 |
| 次优分差 | **100** | 与棋力无关，只控制"备选着法"列表显示几条 |

- **深度 vs 提示强度的区别**：深度是"能力的上限"（资源预算）；提示强度是"故意用几成能力"
  （教学降智）。"最强(不限) + 深度 16"才是满配；"最强 + 深度 6"相当于宣称不降智却只给 6 层预算。
- 旧版本默认深度为 6：已持久化的配置不会自动升级，请在设置里手动改为 16。
- 完美着法表全部就位后，**深度/时间不再影响棋力**（查表瞬间返回、无视这两个参数），
  真正起作用的只剩"提示强度 = 最强"。

## 完美着法表（选读：为什么、是什么、怎么用）

### 为什么要提前算？引擎不是已经够强了吗

搜索引擎的本质是"**现场思考**"：遇到局面往前推演十几步，再用评估函数打分挑最好的。
它天生看不远——本游戏破解结论是**最深的必胜路要走 125 步**，一个搜索深度 7~10 的引擎在
开局时根本看不到 125 步外的胜负，只能靠评估函数去"猜"，猜就会有错。

而游戏局面总数有限（约 188 亿），可以**提前把每个局面的真实胜负一次算死，存成表**。
之后遇到任何局面直接查表：炮必胜局面在着法里挑走完后仍必胜的、兵必胜同理、和棋挑保和着、
必败挑抵抗最久的——瞬间返回且**永远正确**，因为它不是在猜。

> 类比：引擎 = 聪明人现场做题，难题会错；查表 = 考前把整本题库的答案背下来，做题 = 翻答案。

一个具体例子（开局，中间变体）：理论上此局面是**和棋**，且唯一不亏的着法是中炮跳吃
`c0c2`——侧炮跳吃 `b0b2` 看着同样在吃子、引擎评分也几乎相同，但它是慢慢输掉整局的败招。
深度 7 的引擎看不出两者的区别（要到一百多步后才见分晓），可能就推荐 `b0b2`；
查表永远知道答案。另外查表是**瞬时**的，还附带一路推演到终局的完整主线；引擎每步要花满
配置的搜索时间。

### 既然有引擎为什么还要查表（以及为什么两个都留着）

两者是**主力与备胎**的关系：查表给理论最优，引擎在三个场景不可替代——

1. **兜底**：对应的层表还没算好、表文件丢失、或分发时没带表，工具照样能用；
2. **降智陪练**：提示强度选 1~5 档时，需要"故意只看 2~6 层"的引擎，查表被跳过；
3. **开发验证**：引擎对弈、开局对照破解结论，是验证求解器正确性的基准。

提示面板右上角的标签区分来源：**"引擎 + 深度 N"** = 搜索引擎现场推演了 N 层；
**"求解器 + 深度 99"** = 查表给出完整求解的着法（99 是"无深度限制"的约定标记）。
表未算全时，未覆盖的局面显示前者，属正常现象。

### "层"是什么？为什么从兵少往兵多算

表按**剩余兵数 k** 分层（k=3..15，共 13 层）。炮每吃一个子兵数减一（k → k-1），
所以判断"剩 8 兵局面"的胜负必须先知道所有"剩 7 兵"的结果——只能从小到大逐层算。
剩 3 兵即终局（炮胜），是天然的起点。

### 数据有多大、存在哪里、要不要重算

每个局面只需存一个答案（炮胜/兵胜/和，2 bit，4 个局面打包 1 字节），
188 亿局面共约 **4.7GB**，按层分成 `layer_3.bin ~ layer_15.bin`。
兵越多局面组合越多，中间层最大（k=10~12 各约 750~810MB）。

存放位置（按此顺序查找）：

1. 环境变量 `SANPAO_TABLES` 指定的目录；
2. **exe 同目录下的 `tables\`**（便携分发用，把文件夹随程序拷走即可）；
3. `%APPDATA%\sanpao\tables\`（默认，与配置文件同目录）。

**打包给别人用不需要重算**——表是纯数据文件，谁拿到都直接查。
若嫌 4.7GB 大：三值数据压缩率很高（zstd 预计可压到几百 MB），或干脆不带表分发，
对方仍可用内置搜索引擎（中局约 10 层深度），只是非理论最优。

### 怎么生成 / 续跑

```bash
cd server && cargo run --release --features solver --bin solver   # 逐层求解 k=3..15, 断点续跑(已有层自动跳过)
```

单线程数小时（实测约 155 万局面/秒），每层算完立即落盘，中断不作废。
求解完成时 CLI 会自动打印开局对照验证（对照 [0irina/lang-chi-yang-qi](https://github.com/0irina/lang-chi-yang-qi)
的破解结论：中间变体开局应为和棋、唯一不亏着法为中炮跳吃 c0c2）。

### 工具如何使用表

提示档位为 0 且当前局面对应层表存在时，自动优先查表（严格最优，分数显示为
"N 步胜"，主线沿表推演到终局）；表缺失或档位 ≥1 时回落到搜索引擎。
运行时按 mmap 内存映射加载当前兵数对应的一层，不占堆内存，由操作系统按需换页。

### 表和程序是解耦的：边算边用，算完无需重新打包

表是**外部数据文件**，程序每次查表时实时读磁盘（找不到该层就用搜索引擎兜底）。
因此求解未完成时即可正常打包安装使用：已算出的层（如剩兵 ≤8）查表给完美着法，
其余局面走引擎；后台每算完一层写入 `%APPDATA%\sanpao\tables\`，
**已安装的程序下一次查表时自动发现新文件，逐层变为完美着法**——不需要重装、
重启或重新打包（查表代码早已在程序里，"长"出来的只是数据）。

分发同理：安装包本身不含表，给别人 = 安装包 + `tables\` 文件夹（exe 旁或
`%APPDATA%\sanpao\tables\`），纯数据拷贝。若想把压缩版表打进安装包一步到位，
才需要等表算完后再打一次包——可选项，非必须。

### 已知偏差与验证

- 表的"和"为**图语义**（双方都无法强制取胜的无限回避），极慢的杀棋线路若需超过 60 步
  静着，实战中可能被"无吃子和棋"偷和——已知且接受的近似；
- 正确性验证：k=4 全层 306 万局面抽查全部符合博弈值定义；oracle 端到端走子合法性通过；
  组合索引/Gosper 枚举单测覆盖；
- **开局对照 0irina 破解结论，完全吻合**：中间变体开局表值 = 和棋，唯一不亏着法为
  中炮跳吃 c0c2，其余 7 着均判兵胜；
- **本项目新算出的结论**：标准开局（炮 a0/c0/e0）表值 = 兵胜，10 种开局走法全部
  判炮方败——执炮想要理论生路必须下中间变体，且自 c0c2 起每步唯一；
- 分布规律：兵越多炮方胜率越低（k=8 层炮胜 43% → k=12 层 0.2% → k=14/15 层为 0），
  满编 15 兵时炮方不存在任何强制胜利。

## 识别说明（重要）

- 监听启动时目标窗口必须显示**标准开局局面**（识别由此自举网格与两方颜色）
- 之后自动跟踪走子；误读会因违反规则被校验拒绝
- 界面左侧镜像棋盘即识别结果，可随时肉眼核对
- 要求两方棋子颜色视觉可区分（红/蓝、黑/白等），棋盘为规整的 5×5 网格
